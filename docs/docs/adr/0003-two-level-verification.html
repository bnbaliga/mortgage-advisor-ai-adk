ADR-0003: Two-Level Identity Verification

Status

Accepted

Date

2026-11-05

Context

Loan servicing requires protecting customer account information while maintaining usability. We need to verify caller identity before providing: - Information access: Balance, payment history - Account changes: Autopay, payment date - Financial transactions: One-time payments

Different operations have different risk profiles and should require proportional verification.

Decision

We implemented a Two-Level Verification System:

Level 1: Basic Verification

  • Factors: Full name + Last 4 digits of phone number
  • Grants access to: Balance, payment history, payoff quote
  • Implementation: verify_customer(full_name, phone_last_4)

Level 2: Strong Verification

  • Factors: Date of birth + Approximate loan balance (within $5,000)
  • Grants access to: Payments, autopay, date changes
  • Implementation: verify_customer_strong(dob, approximate_balance)

State Machine

                     ┌─────────────────┐
                     │  UNVERIFIED     │
                     │  (No access)    │
                     └────────┬────────┘
                              │
                     verify_customer()
                              │
                     ┌────────▼────────┐
                     │     BASIC       │
                     │  (Read access)  │
                     └────────┬────────┘
                              │
                     verify_customer_strong()
                              │
                     ┌────────▼────────┐
                     │     STRONG      │
                     │ (Full access)   │
                     └─────────────────┘

Lockout Logic

# 3 failed verifications = locked for entire call
if call.failed_verifications >= 3:
    call.locked = True
    return {"blocked": True, "reason": "Too many failed attempts"}

Consequences

Positive

  • Proportional security: Low-risk actions need less verification
  • Better UX: Caller can check balance with just name + phone
  • Fraud protection: Financial actions require additional factors
  • Clear audit trail: Verification state tracked per call

Negative

  • Knowledge-based auth limits: Sophisticated fraud could research answers
  • Phone number dependency: Requires accurate customer phone data
  • Balance approximation: $5,000 tolerance is arbitrary

Mitigations

  • 3-attempt lockout limits brute force attempts
  • Call-scoped lockout requires new call to retry
  • Phase 2: Voice biometrics for additional factor
  • Phase 2: Device-based authentication option

Alternatives Considered

Option 2: Single-Level Verification (Rejected)

Require same verification for all operations.

Rejected because: - Poor UX for simple balance inquiries - Over-verification for low-risk operations

Option 3: Voice Biometrics (Deferred)

Use voiceprint matching for identity verification.

Deferred because: - Requires enrollment flow - Higher implementation complexity - Planned for Phase 2

Option 4: SMS OTP (Rejected)

Send one-time password to registered phone.

Rejected because: - Breaks voice-only experience - Latency for SMS delivery - Caller may not have phone in hand
