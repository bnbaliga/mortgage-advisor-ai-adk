ADR-0005: Three-Step Payment Authorization Flow

Status

Accepted

Date

2026-11-10

Context

Processing payments over voice AI requires: - Consumer protection: Prevent unauthorized transactions - Compliance: Clear authorization record - User experience: Natural conversation flow - Error prevention: Avoid accidental payments

We must design an authorization flow that balances security with usability.

Decision

We implemented a Three-Step Authorization Flow:

Step 1: PREPARE

Agent stages the payment with details:

prepare_payment(amount=1500, method="bank_5678", date="today")
# Sets call.pending_authorization = {amount, method, date}
# Returns confirmation details for read-back

Step 2: READ-BACK

Agent reads back details and asks for explicit authorization:

Agent: "So I have a payment of $1,500 from your Chase account
        ending in 5678, scheduled for today. Do I have your
        authorization to proceed with this payment?"

Step 3: CONFIRM

Only after explicit “yes”, agent confirms:

confirm_payment(authorized=True)
# Policy gate checks:
#   - call.pending_authorization exists
#   - authorized=True
#   - identity_strength == STRONG
# Executes payment, returns confirmation number

State Machine

┌─────────────────┐
│  No Payment     │
│  Pending        │
└────────┬────────┘
         │
    prepare_payment()
         │
┌────────▼────────┐
│  Payment        │
│  Staged         │◄──── Caller can say "wait" or "no"
│                 │      to cancel and restart
└────────┬────────┘
         │
    confirm_payment(authorized=True)
         │
┌────────▼────────┐
│  Payment        │
│  Confirmed      │
└─────────────────┘

Policy Enforcement

# confirm_payment blocked without prepare
if tool.name == "confirm_payment":
    if call.pending_authorization is None:
        return _block("No payment prepared. Use prepare_payment first.")

    if not args.get("authorized"):
        return _block("Cannot confirm without 'authorized=True'")

Consequences

Positive

  • Clear consent: Explicit “yes” required, not implicit
  • Audit trail: prepare + confirm sequence logged
  • Error recovery: Caller can cancel before confirm
  • LLM guardrail: AI cannot skip read-back (policy enforced)

Negative

  • Longer flow: 3 steps vs immediate processing
  • Conversation overhead: Read-back adds ~10 seconds
  • State complexity: Must track pending_authorization

Mitigations

  • Conversational read-back: Natural phrasing, not robotic
  • Quick confirm: “Yes” or “that’s correct” accepted
  • State cleanup: pending_authorization cleared after confirm/cancel

Alternatives Considered

Option 2: Single-Step Payment (Rejected)

“Pay $1500” → immediate execution.

Rejected because: - No explicit authorization captured - Accidental payments from mishearing - No audit trail of consent

Option 3: PIN Confirmation (Rejected)

Require caller to enter PIN via keypad.

Rejected because: - Breaks voice-first experience - Requires PIN enrollment flow - Not all callers have PIN set up

Option 4: SMS Confirmation (Rejected)

Send SMS with confirmation link.

Rejected because: - Breaks voice-only experience - Latency for SMS delivery - Many callers want immediate processing
