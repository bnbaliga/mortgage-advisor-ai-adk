ADR-0002: Rules in Code, Not Prompts

Status

Accepted

Date

2026-11-01

Context

Mortgage lending requires strict compliance with: - State-specific lending regulations (Texas HELOC restrictions, California equity rules) - Federal requirements (TILA, RESPA) - Internal business rules (verification requirements, payment limits)

We must decide where to enforce these rules: 1. In LLM prompts - Instructions tell AI to follow rules 2. In code - Tools and policy layer enforce rules programmatically

Decision

We chose Rules in Code via a policy door pattern.

Implementation

# policy.py - Before tool callback validates every call
async def mortgage_gate(tool, args, context) -> Optional[dict]:
    call = get_call_state(context.session.id)

    # Rule: Sam cannot access servicing tools
    if call.active_agent == "triage" and tool.name in SERVICING_TOOLS:
        return _block(call_id, tool.name, args, "agent_access",
                     "Transfer to Ivy for servicing questions")

    # Rule: Balance requires basic verification
    if tool.name == "get_loan_balance" and call.identity_strength < BASIC:
        return _block(call_id, tool.name, args, "not_verified",
                     "Ask for name and phone last 4")

    # Rule: Payment requires strong verification
    if tool.name == "confirm_payment" and call.identity_strength < STRONG:
        return _block(call_id, tool.name, args, "need_strong_verify",
                     "Complete DOB + balance verification first")

    return None  # Allow

Consequences

Positive

  • Testable: 242 unit tests verify rule behavior
  • Deterministic: Same inputs always produce same outputs
  • Auditable: Code changes tracked in git, reviewable
  • Fail-safe: If rule check fails, operation blocked (never approved by default)
  • LLM-independent: Rules work regardless of model version or prompt injection

Negative

  • Less flexible: Rule changes require code deployment
  • More code: Each rule needs explicit implementation
  • Two sources: Prompts still guide conversation, code enforces rules

Mitigations

  • Automated deployment (CI/CD) enables rapid rule updates
  • Rule engine pattern allows rules to be data-driven in future
  • Clear separation: Prompts for tone/conversation, code for compliance

Alternatives Considered

Option 2: Prompt-Based Rules (Rejected)

You must NEVER approve a HELOC for Texas investment properties.
You must ALWAYS verify identity before showing balance.

Rejected because: - Not testable (can’t unit test LLM instructions) - Vulnerable to prompt injection - Model updates could change behavior - No audit trail for rule violations

Option 3: Hybrid with Guardrails API (Deferred)

Could add Google’s guardrails API as additional layer. Deferred to Phase 2.
