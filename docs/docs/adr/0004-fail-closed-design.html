ADR-0004: Fail-Closed Design

Status

Accepted

Date

2026-11-01

Context

The mortgage AI system handles regulatory compliance and financial transactions. When the system encounters: - Unknown states without documented rules - Missing input data - Ambiguous eligibility scenarios - System errors during tool execution

We must decide the default behavior: fail open (allow) or fail closed (deny).

Decision

We chose Fail-Closed Design - when in doubt, deny and escalate to human.

Implementation Examples

# Unknown state = not eligible
def check_heloc_eligibility(state: str, property_type: str) -> dict:
    if state not in KNOWN_STATES:
        return {
            "eligible": False,
            "reason": f"I don't have lending rules for {state}",
            "action": "transfer_to_loan_officer"
        }
# Missing verification = block tool
async def mortgage_gate(tool, args, context) -> Optional[dict]:
    if tool.name in REQUIRES_VERIFICATION:
        if not call.verified:
            return {"blocked": True, "reason": "not_verified"}
# Confirm without prepare = block
if tool.name == "confirm_payment":
    if call.pending_authorization is None:
        return {"blocked": True, "reason": "no_pending_payment"}

Fail-Closed Scenarios

Scenario Fail-Closed Behavior
Unknown state “I don’t have rules for that state, let me transfer you”
Credit score missing Don’t estimate rate, ask for credit range
Verification failed 3x Lock account access, transfer to LO
Payment not prepared Block confirm_payment, require prepare first
Tool execution error Apologize, don’t retry with fabricated data

Consequences

Positive

  • Safety: Never approve something we can’t validate
  • Compliance: Regulators prefer conservative defaults
  • Trust: Callers escalated to humans for edge cases
  • Auditability: Clear decision trail (blocked vs allowed)

Negative

  • Higher transfer rate: More calls go to humans
  • Caller friction: Some valid requests require escalation
  • LO workload: Humans handle edge cases AI can’t

Mitigations

  • Expand known states as we validate rules
  • Clear escalation messaging so callers understand why
  • Lead capture for after-hours edge cases

Alternatives Considered

Option 2: Fail-Open (Rejected)

Allow operations when rules are ambiguous, with disclaimers.

Rejected because: - Regulatory risk (we might violate unknown state laws) - Trust erosion (incorrect information damages reputation) - Harder to audit (unclear what was allowed vs validated)

Option 3: Probabilistic (Rejected)

Use LLM confidence scores to decide allow/deny.

Rejected because: - LLM confidence not calibrated for compliance - Inconsistent behavior between calls - Not auditable (“70% confident” is not a valid approval)
